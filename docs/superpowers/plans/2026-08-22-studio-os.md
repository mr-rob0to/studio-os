## Product scope

Studio OS is an internal animation-studio brief application. A teammate submits a brief, the system persists it, a configured model provider produces validated decision-oriented analysis, and the interface presents the result or a recoverable failure state.

The release includes brief submission, persistence, list and detail views, structured analysis, retry, PGlite locally and in tests, Neon in preview and production, a database-aware health endpoint, Vercel deployment, and contributor documentation.

Authentication, editing, deletion, collaboration, uploads, queues, model routing, external monitoring, and additional product capabilities remain outside this plan.

## Technical constraints

- Use the Next.js App Router with strict TypeScript and plain CSS.
- Keep pages and layouts as Server Components unless browser interaction requires a client boundary.
- Use Zod for input, output, and API contracts.
- Use one Drizzle PostgreSQL schema and committed migrations for PGlite and Neon.
- Keep application database composition platform-neutral: runtime modules must not read Vercel or another hosting provider's environment variables.
- Require explicit `APP_ENV=local|test|preview|production` and `DATABASE_DRIVER=pglite|neon` configuration; do not default a missing database driver to PGlite.
- Allow PGlite only for `local` and `test`; reject it for `preview` and `production`, and require a server-only `DATABASE_URL` whenever the Neon driver is selected.
- Treat provider output as `unknown`; validate it centrally before persistence or rendering.
- Persist the brief and pending analysis before provider execution.
- Retry must claim an analysis atomically and recover stale pending work.
- Builds must not connect to a database or model provider.
- Pull request CI must prove committed migrations apply to clean PGlite and reject Drizzle schema changes without matching committed migration history.
- Vercel Git integration owns deployments: pull requests create previews and changes to `main` create production builds.
- GitHub Actions owns tests and database migrations only; it must not deploy the application.
- Every successful update to `main` must pass the full quality gate and run the idempotent committed migrations against production Neon.
- Vercel must hold production promotion until the stable GitHub production-migration check passes. A failed migration must prevent the new build from becoming live.
- Production migrations must remain backward-compatible because Vercel can build before the migration check finishes.
- Every non-docs task receives exactly one fresh read-only Claude Code Fable review after its pull request is open and the branch is finished.
- Every task uses a standard short-lived feature branch; use a worktree only when genuinely parallel work requires more than one active checkout.
- New capabilities, external services, or more than 30 minutes of unplanned work require a scope checkpoint.

## Release readiness acceptance

- Pull request CI fails when Drizzle schema changes are not represented by committed migration history.
- Pull requests apply all committed migrations to clean PGlite before lint, typecheck, tests, and build.
- Every update to `main` passes the same complete quality gate before the production migration job begins.
- Every update to `main` runs the idempotent committed migrations against production Neon, without path-detection logic.
- `main` workflow runs are serialized and never canceled after migration begins.
- Migration failure fails `Production database migration`, and Vercel keeps the previous production deployment live.
- Vercel Git integration creates pull-request previews and production builds; GitHub Actions never deploys the application.
- GitHub stores only the protected production migration `DATABASE_URL`; Vercel stores its own runtime database, provider, `APP_ENV`, and `DATABASE_DRIVER` settings.
- Pull requests use clean PGlite migration validation and do not create preview Neon databases or database branches.
